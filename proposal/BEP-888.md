## Abstract

This proposal describes transferable shares backed by a basket of on-chain Meme tokens, proportional in-kind redemption, and an entry point that purchases components with BNB, deposits proportional amounts, issues shares, and refunds unused assets in one transaction. The deployed dIDX reference basket has four fixed components. Its shares can also serve as a quote asset in MemeDAQ launch pools.

“BEP-888” is the project's name and working identifier. Publishing this repository or deploying contracts does not establish an official BNB Chain proposal number, submission, acceptance, or endorsement.

## Motivation and practical contribution

Several tokens can emerge around the same Meme theme. A user wishing to participate across them otherwise has to acquire and manage each position. A redeemable basket provides one position representing proportional interests in several actual reserves, with a shared entry point that communities can use together.

For example, a future BROCCOLIIDX could represent selected Broccoli-themed tokens. That would offer combined exposure without requiring a user to continually choose between individual tokens. It would not merge existing tokens, pools, or communities. Arbitrary Broccoli baskets are not currently supported, and improvements in community participation remain an outcome to measure.

The contribution is a concrete composition: Meme-oriented basket shares, atomic native-currency entry with component refunds, measured net receipts, separate baskets with separate entitlements, and use of shares as a Meme pool quote asset. This proposal does not claim to have invented redeemable baskets or proven universal technical novelty.

## Scope

- V1 reserve and gateway arrays have exactly four entries. General N-asset baskets require a new implementation.
- Components are fixed at basket construction. The basket has no administrator withdrawal, upgrade, rebalance, or component-replacement function.
- The five-candidate registry allows the launchpad owner to bind a fifth platform-token candidate once and register separately initialized four-component baskets. This is not permissionless arbitrary basket creation.
- A token name ending in `IDX` does not grant reserve rights. Only the applicable basket's share contract does.

## Specification

All quantities below are integers in the respective token's smallest unit. Let `S` be total share supply, `R_i` the internally accounted reserve, `A_i` the current actual balance, and `B_i = min(R_i, A_i)` the redeemable reserve.

### Initialization

The constructor fixes four distinct contract addresses and an initializer. Initialization can occur once and requires at least `1e6` net units of each component. It issues `1e18` share units: `1e6` are permanently locked at `address(0xdead)` and the remainder goes to the chosen receiver. Shares use 18 decimals. Initializing one nominal share does not fix its USD value.

### Deposit

The basket transfers all four inputs and measures actual net receipts `d_i` from balance differences. It computes:

```text
minted = min_i floor(d_i * S / B_i)
required_i = ceil(minted * B_i / S)
```

The transaction must satisfy `minted >= minShares`, nonzero reserves, a valid receiver, and an unexpired deadline. For each component, `d_i - required_i` must not exceed `floor(d_i * maxSurplusBps / 10000)`. The contract caps this parameter at 1000. Accepted surplus from a direct deposit remains in the basket; it is not returned by the core basket.

Incoming transfer fees are measured rather than credited as collateral. The net-transfer accounting does not imply compatibility with every rebasing, frozen, or fee-bearing token.

### Atomic BNB entry and refunds

`DidxRefundGateway.mintFromBnb` accepts four positive BNB budgets, per-leg minimum outputs, minimum shares, an optional Meme purchase, a receiver, and a deadline. Their sum cannot exceed `msg.value`.

1. Purchase components through the gateway's deployment-bound V2/V3 paths.
2. Isolate this call's acquired balances from pre-existing balances.
3. Compute the share target from current reserves and actual acquired quantities.
4. Approve and deposit only the rounded-up proportional quantities, with **zero surplus tolerance**.
5. Transfer shares to the receiver, or use them to buy the specified Meme through the configured router.
6. Clear temporary allowances and return unused component tokens and native BNB to the payer, `msg.sender`.

The receiver and payer may differ. Refunds are not resold into BNB. Incompatible extra transfer taxation into the basket, missed output limits, expiry, or a failed refund revert the entire transaction. A legacy `maxSurplusBps` argument is retained in the entry ABI but does not relax its zero-surplus deposit rule.

The full ABI and refund event are documented in [the entry-point guide](../docs/didx-bnb-mint.md). The implementation is [DidxRefundGateway.sol](../src/index/DidxRefundGateway.sol).

### Redemption

For each component:

```text
gross_i = floor(shares * B_i / S)
```

The basket burns only the caller's shares. Minimum outputs apply to the recipient's measured net balance increases after transfer tax. Abnormal transfers that deduct more than the intended amount from the basket are rejected. A zero reserve does not by itself prevent withdrawal of other components; a nonzero component that refuses transfer can revert the whole exit.

In-kind redemption does not need a USD oracle. The separate `DidxGateway.redeemToBnb` flow additionally depends on each swap path, liquidity, per-leg output limits, and the final BNB minimum. It needs allowance to pull the user's shares; direct basket redemption does not.

### Accounting and authority

Unaccounted donations do not increase `B_i`. A balance shortfall is shared proportionally through the `min` rule. The initializer is not an ongoing reserve administrator. There is no reserve rescue or admin seizure path in this basket.

Other contracts have different authorities: the launchpad controls quote configuration and launch settings, the registry is owner-managed through the launchpad's owner, and the price index supports delayed component proposals. These permissions do not change the fixed reserve basket. See the [permissions matrix](../docs/PERMISSIONS.md).

### NAV, index points, and executable quotes

Reference NAV is the USD value of redeemable component quantities divided by share supply. Reference index points track price performance against component baselines and weights. They are separate measurements.

Website spot estimates are display data. Launch valuation still uses validated on-chain price feeds. Deposits and in-kind redemption use actual reserve ratios; BNB conversion quotes require simulation and user-approved minimum outputs. Additional proportional minting does not itself increase NAV per share.

## Rationale and compatibility

Fixed components make the V1 reserve and route boundary explicit. Quantity-based proportional accounting keeps a USD oracle out of core issuance and in-kind redemption. Raw-token refunds avoid an additional swap. Shares implement the base ERC-20 interface; this multi-asset interface does not claim ERC-4626 compatibility.

Every composition is an independent share contract. Interfaces must bind balances, approvals, previews, and execution to the same selected basket. Switching a selection must not imply migration of existing holdings.

The current core basket is immutable. N-asset support and any future migration need explicit new code and an explicit user flow. Existing owners of shares cannot be silently migrated by changing the website.
